## Intent

Operator request 2026-09-23 (with a watch-face screenshot, bottom-left slot): build a new circular watch complication modelled on the current Trio **contact-image** complication — the one in the bottom-left slot of the screenshot: purple/blue trend ring, `211` centered, `<1 m -1` beneath — but as a native WidgetKit complication and with these differences:

- **No outer white ring.** The contact-image version draws a white circle border around the whole face; drop it entirely.
- **Glucose bobble as large as possible.** The bobble is the trend indicator — maximize its diameter within the `accessoryCircular` bounds rather than insetting it for the ring.
- **Center: current BG**, large, as in the screenshot's `211`.
- **Beneath it: delta + recency**, styled like the existing `accessoryCorner` complication's secondary line (e.g. `<1 m -1`), but **without the BLE/connection indicator** the corner variant shows.

Reference screenshot: `~/.claude/uploads/98f4daf1-40b8-4772-a530-24af0d9454ec/e395d84f-image.png` (watch face, 2026-09-23 20:16; bottom-left slot is the current contact-image complication).

The corner variant is the reference for the delta + recency line; reuse its formatting rather than re-deriving it.
- `Trio Watch Complication/TrioWatchComplicationPreview.swift` — every existing preview uses `family: .accessoryCorner`; add circular previews covering the same states (fresh, stale, no-data, high/low colors).
- Data comes from `TrioComplicationDataStore` (App Group snapshot: glucose, trend, delta, readingDate, glucoseColor) — no new plumbing expected.
- Ships via patch 09 (`09-watch-g7.patch`), so the work goes on `feature/watch-g7` and the patch is regenerated. Any NEW file needs `--extra-files` on regeneration (CLAUDE.md "Patch regeneration: new files" — a dropped `.swift` fails only at build time as "cannot find <Type> in scope").

## Findings that shape the plan (verified against `upstream/dev`)

1. **`Trio Watch Complication/TrioWatchComplication.swift` is upstream code** — good; a new widget kind belongs there naturally. But `Trio Watch Complication/TrioWatchComplicationPreview.swift` and `Trio Watch Shared/TrioComplicationDataStore.swift` are **fork-only** (added by patch 09).

2. **Upstream's complication carries no glucose data.** `TrioWatchComplicationEntry` is `struct { let date: Date }`; the provider returns one entry with `policy: .never`; `TrioAccessoryCircularView` renders `Image("ComplicationIcon")`; the widget's description is literally "Displays Trio app icon as complication". So upstream has **no** App Group snapshot store, no writer, and no refresh scheduling for complications — the fork's `TrioComplicationDataStore` + `ComplicationLogBuffer` + reload machinery (patch 09) is what makes a data-bearing complication possible here.

   Consequence: a PR that adds a *working glucose* complication upstream would have to bring that entire pipeline with it. That is not a clean or easy PR, and it is the same pipeline TRIO-054's comparison AC is about.

3. **The requested design already exists upstream as a parameterized view.** `Trio/Sources/Services/ContactImage/GlucoseBobbleContactView.swift` (upstream, 90 lines) takes exactly: `glucoseText`, `minutesAgoText`, `deltaText`, `glucoseColor`, `rotationDegrees` — and renders an angular-gradient ring with the BG centered and a minutes-ago + delta line beneath. That is the requested complication, already abstracted. The abstraction the operator hoped for is therefore close to free; the only real work is that the view currently lives in the phone target and would need to move to a location both the phone and the watch complication target can compile against.

## Recommended split (needs operator sign-off before implementing)

- **Upstream PR (clean and small):** relocate `GlucoseBobbleContactView` to a shared location compiled by both targets, and parameterize the outer ring (the white circle the operator wants dropped) — e.g. an explicit `showsOuterRing` / inset parameter with the current behaviour as the default so the contact image is unchanged unless opted in. No behaviour change, no new data path. This also delivers TRIO-054's visual ask on the contact-image side, so the two tasks should be sequenced together or merged.
- **Fork side (patch 09):** convert `@main struct TrioWatchComplication: Widget` into a `WidgetBundle` with a second widget kind (distinct `kind` string and `configurationDisplayName`, `supportedFamilies` = `[.accessoryCircular]`), whose timeline provider reads `TrioComplicationDataStore` and feeds the shared view. Add previews alongside the existing corner ones. This part stays fork-only until upstream has a complication data pipeline.
- **Deliberately not doing:** upstreaming the complication wiring or the data store as part of this task. If the operator wants a data-bearing complication upstream, that is its own (large) task.

## Clarifications and verified answers (2026-09-23, round 2)

- **WidgetKit complication** (`Trio Watch Complication/TrioWatchComplication.swift`, upstream): upstream ships it **icon-only**. `TrioWatchComplicationEntry` is `{ let date: Date }`, `TrioAccessoryCircularView` renders `Image("ComplicationIcon")`, description "Displays Trio app icon as complication". No glucose, no data store, no refresh policy upstream. The statement "upstream's complication has no glucose data" applies **only** to this one.
- **Contact-image ("contacts") complication** (`Trio/Sources/Services/ContactImage/*`, upstream): fully data-bearing upstream — `ContactImageManager` builds `ContactImageState` and `ContactPicture` renders it, including the `.bobble` style via `GlucoseBobbleContactView`. This is what the screenshot's bottom-left slot shows.

### What draws the white ring (answer to the operator's question)

`ContactPicture.getImage` draws `contact.ring` **before** the style switch, for every style including `.bobble`:

- The enum is `ContactImageLargeRing` with only two live cases: `.none` (displayName "Hidden") and `.loop`.
- `ringColor()` returns `.loopGreen` (≤5 min since `lastLoopDate`), `.loopYellow` (≤10 min), `.loopRed` (>10 min), and **`.loopGray` when `state.lastLoopDate` is nil**. `lastLoopDate` is `lastDetermination?.timestamp` (`ContactImageManager.swift:232`). So the whitish ring is the **loop-status ring in its gray state**, not decoration.
- It also insets `rect` twice — by `outerGap = 0.03`, then by `ringWidth + ringGap` — before the `.bobble` branch sizes the bobble from `min(rect.width, rect.height)`. **That inset is why the bobble cannot be full size.**

Immediate consequences:
1. The operator can remove it today: set that contact's **Ring → "Hidden"** in Trio's Contact Image settings; the bobble also grows, because the inset stops being applied.
2. If the ring shows gray while the loop is healthy, `lastDetermination` is not reaching `ContactImageState` — a genuine upstream bug worth its own small PR. Worth confirming on device before filing (green/yellow/red vs gray).
3. Clean upstream PR candidate for the bobble: skip the outer ring and its inset for the `.bobble` style, since that style draws its own trend ring — one guarded branch in `getImage`, no new API. This is the same ask as TRIO-054's "drop the white ring", so the two should be done as one PR.

## Feasibility: reuse the contact-image config + UI to configure the new complication (2026-09-23)

Operator proposal: rather than invent settings, give the new circular complication its own section in the phone app that mirrors the contact-image configuration, reusing the same model/UI/renderer. Investigated; **verdict: reasonable, and cheaper than expected for the Bobble style — but it splits into three very different pieces of work.**

### What makes reuse genuinely attractive

- **The config is resolution-independent.** `FontSize` raw values are 200/250/300/400 *on a 1024×1024 canvas* (i.e. fractions of it), and `ringWidth`/`ringGap` are used as `rawValue / 100.0` percentages. So the same entry renders correctly at a ~50pt complication size with no re-tuning.
- **`ContactImageEntry` is a plain value type** (`Hashable, Equatable, Sendable`, 20 fields, all enums/Bool/String) apart from `managedObjectID: NSManagedObjectID?`. It already carries `fontWeightString` / `fontWidthString` helpers for storage, so an encodable form is nearly free.
- **`ContactImageState` is already `Codable`** — the live-values half needs no work to travel.
- **The settings screens are already generic over the entry**: `ContactImageDetailView` / `AddContactImageSheet` bind to `$contactImageEntry.<field>` throughout, so extracting the form into a reusable view taking a `Binding<ContactImageEntry>` is a mechanical refactor, not a rewrite.
- Persistence is the Core Data entity `ContactImageEntryStored`, fetched via `contactImageStorage.fetchContactImageEntries()` — a second entry (or a flag/kind column) can represent "circular complication" config.

### The Bobble style is nearly free; the other layouts are not

- **`.bobble` renders in pure SwiftUI** (`GlucoseBobbleContactView`, turned into an image by `ImageRenderer` only because a *contact photo* must be a `UIImage`). In a WidgetKit complication there is no such requirement — the view can be used **directly**, no UIKit and no image rendering at all. Since the Bobble is the style the operator wants, the main path is genuinely cheap.
- **`.default` and `.split` go through `ContactPicture.getImage`**, which uses `UIGraphicsImageRenderer`, `UIColor`, `UIFont`, `UIImage`, `NSAttributedString`, `UIGraphicsGetCurrentContext()` and `UIRectFill`. `UIImage`/`UIColor`/`UIFont`/`NSAttributedString`/`UIGraphicsImageRenderer` are fine on watchOS; **`UIRectFill` and `UIGraphicsGetCurrentContext()` need a compile check** — both have trivial CoreGraphics replacements (`ctx.cgContext.fill(rect)`, and using the renderer's own `ctx.cgContext` instead of the global). Verify with a throwaway watch-target compile before committing to supporting these layouts.

### The real architectural constraint: the config has to travel to the watch

App Groups do **not** span phone and watch — they are separate devices. So unlike the contact image (rendered on the phone, delivered through the Contacts framework), a watch complication needs either:

- **(A) the config sent to the watch and rendered there** — ~20 small fields over WatchConnectivity, sent on change and/or piggybacked on the existing per-cycle watchState dict; the widget composes the view locally. The fork already has exactly this pipeline (`TrioComplicationDataStore` + the watchState payload), so this is the natural fit. **Also the only option that keeps the recency text live**: "1 m +6" must count up between data updates, which only works if the view is composed on-watch. A phone-rendered image freezes the minutes-ago value until the next render — the known weakness of the contact-image path.
- **(B) the phone renders a PNG and transfers it** — reuses 100% of the renderer with zero watchOS-compile risk, but adds a per-cycle image transfer and inherits the frozen-recency problem. Not recommended given (A) already exists here.

### Options that will NOT translate — scope them out

| Setting | Verdict for a watch complication |
|---|---|
| `contactId`, `name` | Contact bookkeeping; irrelevant — omit |
| `backgroundMode` (transparent / black) | Complications must be transparent; watchOS supplies the backdrop. Force transparent, omit the control |
| `colorMode` (color / monochrome) | Partly moot: on tinted watch faces watchOS desaturates the whole complication regardless. Honoured only on full-color faces — keep, but document the caveat |
| `.split` layout | Two values inside a ~50pt circle; legibility risk. Either omit from the picker for this surface or accept it looks poor |
| `hasHighContrast` | Works, arguably redundant at complication size |
| `fontSize` / `secondaryFontSize` / `fontWeight` / `fontWidth` | Work as-is thanks to canvas-proportional values |
| `ring` (loop status) + width/gap | Works; this is the ring worth keeping optional |
| `primary` / `top` / `bottom` value pickers | Work for `.default`; the Bobble style ignores them by design |

### Recommended shape

1. Extract the settings form into a reusable view over `Binding<ContactImageEntry>` with a parameter for the surface, so the complication section reuses the contact form minus the rows in the table above.
2. Store the complication's config as its own `ContactImageEntryStored` row (or a kind/flag), so the two surfaces are configured independently.
3. Send the config to the watch alongside the existing watchState payload; render on-watch — Bobble via `GlucoseBobbleContactView` directly, other layouts only if the UIKit compile check passes.
4. Keep the upstream PR (patch 07, per the numbering plan) to the *view/model* reuse that does not depend on the fork's data store; the transfer + widget wiring stays fork-side until upstream has a complication data pipeline.

### Caveat to settle before building

This is a notably bigger surface than "add a complication": a shared settings form, a second config row, and a config-transfer path. If the goal is primarily the operator's own watch face, implementing the Bobble-only complication with a handful of settings (ring on/off, show minutes, show delta, color mode) costs far less and can adopt the full config reuse later. Recommend deciding that scope explicitly before starting.


## CORRECTION (2026-09-23): a coloured background IS possible — `backgroundMode` maps fine

The feasibility table above claimed "complications must be transparent; watchOS supplies the backdrop". That is wrong, as the operator pointed out: the Dexcom circular complication on their watch face renders a filled glucose-coloured disc behind the value.

Trio already has the exact mechanism, unused. At the bottom of `Trio Watch Complication/TrioWatchComplication.swift`:

```swift
func widgetBackground(backgroundView: some View) -> some View {
    if #available(watchOS 10.0, iOSApplicationExtension 17.0, iOS 17.0, *) {
        return containerBackground(for: .widget) { backgroundView }
    } else {
        return background(backgroundView)
    }
}
```

Both existing views call it with `Color.clear`. Supplying a colour instead is a one-argument change — `containerBackground(for: .widget)` is precisely how Dexcom fills its disc. `AccessoryWidgetBackground()` is also available for the standard translucent system backdrop.

So `backgroundMode` translates directly: transparent → `Color.clear`, black → `Color.black`, and the surface could additionally offer a glucose-coloured fill (Dexcom-style), which the contact-image config has no equivalent for.

### The actual constraint is the watch face's widget rendering mode, not the background

- `.fullColor` — rendered as authored. The operator's face is clearly in this mode (coloured activity rings, the UV gradient, Dexcom's olive disc).
- `.accented` — watchOS splits the view into accented and default groups and tints each; `widgetAccentable()` controls which group a subview lands in. The fork already calls `widgetAccentable()` in two places but never reads `\.widgetRenderingMode`.
- `.vibrant` — desaturated to the face's tint; authored colour is largely discarded.

So the honest caveat is narrower than the table said: **colour and background are fully available on full-colour faces, and are tinted or desaturated on accented/vibrant faces**. A complication that wants to look right everywhere should read `\.widgetRenderingMode` and choose its background and `widgetAccentable()` grouping accordingly — worth doing here, since none of the existing code does.

Same correction applies to the `colorMode` row: it is honoured on full-colour faces rather than "partly moot".

### Phase C design

- `GlucoseBobbleComplicationSettings` (Foundation-only, `Trio/Sources/Models/`, compiled into phone, watch app and complication via the sync config) stored as `TrioSettings.glucoseBobbleComplication`, following the `garminSettings` struct-setting precedent. Decoding is field-by-field with defaults.
- Sent on the existing watch-state message (like `showForecastWatch`): settings as JSON `Data`, plus `lastLoopDate` as a TimeInterval (omitted when the loop is over a day old, matching `lastLoopTime` "--"). Both are in the phone `WatchState` equality and hash so a change is never deduplicated away.
- Upstream watch app: saves settings and the snapshot (now carrying `lastLoopDate`) to the App Group independently and reloads timelines once if either changed.
- Complication: loads settings per timeline; applies colour mode (tint keeps the glucose colour when the number is white), text visibility, background style, and the loop-status ring evaluated per entry date.

### Fork adaptation (patches 09 and 13)

- The fork's watch app never calls upstream's `publishComplicationSnapshot` (its complication reads `TrioComplicationDataStore`), so `publishGlucoseBobbleComplicationInputs()` saves the settings, stores the loop date under its own App Group key (read back by the fork's `GlucoseComplicationSnapshot.load()`), and reloads only the circular complication's kind.
- The fork's background channels send an allowlisted subset; `lastLoopDate` and the settings were added to it (patch 13 owns the latest shape of that allowlist), and the watch takes the loop date whenever present, clearing it only on a full message that omits it. Without this the ring would age to red whenever the watch app is in the background.
- Patch 13 had to be regenerated on top of patch 04's sender lines: patches 09, 10 and 13 rewrite almost all of `watchStateToDictionary`, so 04's lines cannot have upstream-identical context there. Its branch gained 04's three lines as context (commit e15d33c7a).
