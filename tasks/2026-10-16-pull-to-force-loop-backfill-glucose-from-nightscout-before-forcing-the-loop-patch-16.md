## Intent

The Home screen pull-down-to-force-loop (upstream dnzxy f567bef7e, `HomeRootView+Refresh.swift`) should first pull the last 24h of glucose from Nightscout into Trio, then force the loop, so a reading Trio missed over Bluetooth but Nightscout has (via the Dexcom Share gap-fill cron, `device: dexcom-share`) is in the store before determine-basal runs.

Ships as branch `feature/ns-backfill-on-pull` and patch `16-ns-backfill-on-pull.patch`.

## Design decisions

- Store via `GlucoseStorage.backfillGlucose`, not `storeGlucose`. A 91-day raw Nightscout analysis (2026-10-16) found 90 Trio↔Share pairs for the same reading with offsets up to ~30s (43 beyond 1s); `storeGlucose`'s 1s dedup would have duplicated those, `backfillGlucose`'s 3.5-minute window catches all of them. Only this phone's Trio uploads to Nightscout (operator, 2026-10-16).
- The fetch is bounded (~10s) so a slow Nightscout never holds up the loop; unreachable or unconfigured Nightscout returns quickly and the loop still runs.
- The indicator shows a fetching phase, then the existing "Forcing loop…" phase; the existing isLooping wait timers start after the backfill.
- `NightscoutConfigStateModel`'s settings-screen backfill is left unchanged.
- This feeds glucose into a dosing loop; the operator reviews the diff before it ships.

## Release note

Pulling down on the Home screen to force a loop now first fetches the last 24 hours of glucose from Nightscout, so a reading Trio missed over Bluetooth but Nightscout has (for example a Dexcom Share fill) is stored before the loop runs. The indicator shows "Fetching Nightscout glucose…" and then "Forcing loop…"; the fetch gives up after 10 seconds, and the loop runs either way.
