# Feature branch workflow optimization (fork + patch stack) — v3 (mailbox patches)

This repository is a personal fork of an upstream repository.

- Upstream: `nightscout/Trio` (branch: `dev`)
- Fork: `cachrisman/Trio` (branch: `dev`)

The fork maintains a **patch stack**: patch files in `./patches/` that represent:

1) changes waiting for upstream approval/merge, and/or  
2) long‑lived divergences you keep in your fork.

## Operating model

### Weekly CI (automation)
GitHub Actions runs **weekly** to:

1) sync fork `dev` with upstream `dev`,  
2) apply patches in `./patches/` **in order**,  
3) build and deploy a TestFlight build.

### Local ship (manual, primary)
Day-to-day development and shipping happens **locally** using `ci/local-build.sh`:
- **Build-only** to validate (fast feedback, no upload)
- **Release-only** to upload an already-built IPA (short step)

CI remains for the weekly upstream sync/build, not for ad-hoc shipping.

---

## Goals

**G1.** Fork stays current with upstream `dev`.  
**G2.** Patch stack is reproducible: clean base + apply all patches succeeds.  
**G3.** One feature = one patch file (deterministic ordering via numeric prefix).  
**G4.** Local dev is branch‑based (commit often); avoid relying on dirty worktrees.  
**G5.** Releases are traceable: each build can list included patches.  
**G6.** **Target state:** patch stack uses **mailbox patches** applied via `git am` (commits + provenance).  
**G7.** Big‑bang cutover: once implemented, the legacy patch format stops being used.

---

## Rules (invariants)

1) **Never hand‑edit patch files to fix apply failures.** Fix code and regenerate patch.  
2) After syncing upstream, **re‑test that all patches apply in order**.  
3) **One patch per feature**. Split large work into multiple explicit patches only when necessary.  
4) Patch files in `./patches/` are the source of truth and are committed to fork `dev`.  
5) Feature branches may have many commits; **patch generation is the "publish" step**.  
6) Rewriting history is fine on feature branches; **avoid rewriting `dev`** unless you know you need it.  
7) Default builds should not upload; uploading is explicit (release-only).
8) When editing workflow/plan docs, increment the document version and update the changelog in the same change.

## Patch file format and naming

### Target patch format
- **Mailbox patch** generated by `git format-patch` (single-commit mailbox patch).
- Applied with `git am` (creates a real commit with author/date/message).

### File extension
- Patch files are mailbox patches and always use the `.patch` extension.
- They are applied with `git am`.

## Sync fork `dev` with upstream `dev` (local)

### One-time setup

```bash
git remote add upstream https://github.com/nightscout/Trio.git
git fetch upstream
```

### Regular update

```bash
git checkout dev
git fetch upstream
git pull origin dev
git merge upstream/dev
git push origin dev
```

After syncing, re-run patch validation (below).

> If you prefer a linear fork history, you can `git rebase upstream/dev` and force-push. Only do that if you understand the consequences for your fork and any collaborators.

## Publish as a patch file (mailbox patch)

**Recommended:** keep a dedicated **dev worktree** and run patch tooling from there, so you never accidentally use stale scripts.

### 0) One-time: create a dev worktree

From the main repo directory:

```bash
git worktree add ../Trio-dev dev
```

The `../Trio-dev` directory becomes your canonical location for:
- `./scripts/generate-patch.sh`
- `./scripts/patch-test.sh`

### 1) Implement fixes on a feature branch

```bash
git checkout dev
git pull origin dev
git checkout -b feature/<short-name>
# commit normally; squashing is optional and not required
```

### 2) Generate (or update) a patch from the dev worktree

```bash
cd ../Trio-dev

# Create a NEW patch (auto-numbered)
./scripts/generate-patch.sh -n -s feature/<short-name> -t dev -d "short-description"

# UPDATE an existing patch by writing directly to its filename
# (example updates patch 06)
./scripts/generate-patch.sh -n -s feature/<short-name> -t dev -o patches/06-short-description.patch -y
```

Notes:
- Patch generation happens against the **patched dev baseline** (the tool applies the existing patch stack first), so conflicts are surfaced early.
- Patch generation is intentionally **forbidden** from including infra/tooling paths (e.g. `scripts/`, `ci/`, `.github/`, `fastlane/`, `patches/`). Those changes must be committed directly to `dev`.

### 3) Validate patch application before committing

Run the canonical patch-stack validation script:

```bash
scripts/patch-test.sh
```

This script encapsulates the worktree-based clean-`dev` flow and applies patches using `git am`:
- applies the full existing patch stack in order
- applies the candidate/generated patch
- fails fast on the first error
- cleans up any temporary worktrees/state

If validation fails:
- do **not** hand-edit patch files
- fix code in a feature branch
- regenerate the patch (via `generate-patch.sh`)
- re-run `scripts/patch-test.sh`

### 4) Commit the patch file to fork `dev` (only after successful testing)

```bash
# After successful patch testing, commit the patch file
git checkout dev
git add patches/NN-<desc>.patch
git commit -m "patches: add NN-<desc>"
git push origin dev
```

Patch files live on fork `dev` because CI checks out fork `dev` and reads `./patches/`.

## Multiple features simultaneously

- Independent features: separate patches, ordered by numeric prefix.
- Dependent features: order patches so prerequisites apply first.
- If two patches conflict and both are needed:
  - prefer refactoring to remove the conflict, or
  - introduce an explicit small "glue" patch that resolves the conflict, e.g. `patches/12-glue-a-b.patch`.

Avoid using “apply patch A onto feature branch B” as the normal approach; instead, publish both patches and let the stack define the combined state.

## Local builds (authoritative, mirrors CI state)

Use `ci/local-build.sh` (authoritative).

### Build-only (validate, no upload)

```bash
ci/local-build.sh --base-branch dev --build-only
```

### Release-only (upload existing IPA; fast)

```bash
ci/local-build.sh --release-only
```

Notes:
- `--release-only` expects `./Trio.ipa` to exist (produced by the build-only step).
- This splits “does it build?” from “upload to TestFlight”.

### Build current branch state (skip patches)

```bash
ci/local-build.sh --build-current --build-only
```

### Build dev + patches + your local working changes (explicitly when needed)

```bash
ci/local-build.sh --base-branch dev --reapply-stash --include-untracked --build-only
```

## Build system changes vs product changes

- Product changes (app code) → shipped via patch files in `./patches/`.
- Build/infra changes (`build_trio.yml`, `Fastfile`, `ci/local-build.sh`, patch tooling scripts/docs) → committed directly as normal commits (not patches).

Workflow for build system changes:

1) Create branch: `infra/<name>` or `feature/build-system-<name>`
2) Change files
3) Test locally
4) Commit normally
5) Merge/rebase into fork `dev`
6) Push fork `dev`

Rationale: CI and local shipping depend on these files as part of the fork’s operating system.

## Release recording (what’s in a build)

Minimum viable release record:

- base upstream commit SHA (the upstream `dev` you synced from)
- fork `dev` commit SHA (the one used for build)
- list of patch filenames applied (in order)
- sha256 of each patch file
- timestamp
- build number/version (from Fastlane)

Deterministic inventory commands:

```bash
git rev-parse HEAD

ls -1 patches/*.patch
shasum -a 256 patches/*.patch
```

Store in a `releases/` folder (committed) or as build artifacts. Pick one convention and keep it consistent.
