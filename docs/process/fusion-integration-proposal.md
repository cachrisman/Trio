## Purpose

How to configure [Fusion](https://github.com/Runfusion/Fusion) (a self-hosted AI agent-orchestration tool) to work **with** Trio-dev's existing development process — the 5-step doc-driven feature pipeline **and** the telemetry-gated per-build cadence loop — rather than replacing it. Grounded in the actual process: `.cursor/rules`, `docs/prompts/01–05`, `docs/process/*`, `docs/templates/*`, the `AGENTS.md` (v19) patch-stack model, and recent watch-g7 builds 215/216/217.

## Core principle: Fusion as an orchestration + review layer, not an autopilot

Trio-dev's process is **human-gated, doc-artifact-centric, patch-stack-based, telemetry-verified, and build-averse** — the near-opposite of Fusion's default "autonomously plan → build → verify → merge to main." Therefore:

1. **The on-disk versioned docs stay the source of truth.** Fusion tracks and drives; it does not replace `docs/in-progress/<feature>/{00-feasibility,01-design,02-implementation-plan,03-implementation-log,04-postmortem}.md`.
2. **Fusion never merges to `dev` and never runs iOS builds.** Patch integration (`mid-stack-update.sh`, `repin-g7.sh`, `patch-test.sh`) and builds/TestFlight stay human/script-driven — they are safety-gated (the clobber guardrails exist because a live insulin pod was once silently dropped).
3. **Fusion's real value-add is what you already do by hand:** multi-model review fan-out (crediting cursor/ollama/Opus/Sonnet with specific catches), plus governed telemetry-driven ideation. Fusion automates exactly those.

## Two interleaved loops (both must be modeled)

- **Feature pipeline** (linear, per-feature): design review → create plan → pre-impl doc review → execute → red-team review. Reused *inside* each build iteration.
- **Build cadence** (cyclic, per-build, telemetry-gated): ship → **soak** (~days on-device) → **soak review** (evidence base + Gate-0 GO/NO-GO) → **next-build ideas gathering** (Fable-5 ideation) → select survivors → build plan → execute → red-team → ship → soak. For long-running BLE/hardware initiatives (watch-g7, builds 186→218) this is the **outer** loop.

Critically for the cadence loop: **there is no build/test that proves success** — acceptance (e.g. "RSSI present on those events so distributions are comparable in BetterStack") is measured on the *next* soak. So a task's "done" ≠ "verified"; **verification is deferred to a later soak-review task.** Fusion's verify-then-merge cannot close this loop inside one task — model it as a two-task pattern (ship-task → later soak-review-task).

Concretely (grounded in builds 207–218; see `fusion-workflow-fit-assessment.md`): the "later soak-review task" is a **fan-in**, not a paired partner of one ship-task — one soak-review evaluates *every* arm the prior build shipped and simultaneously gates the *next* build's candidate tasks. Its verdict set is **not binary**: it includes **re-defer** (carry acceptance to the following soak — e.g. Task C "deferred to 217, gated on W-7's soak", `build216-impl-log.md:14,54`) and **premise-confirmed-but-sequence-later** (`build217-impl-plan.md:39-43`). And an **instrumentation ship** is a special case whose acceptance is *ideation unblocking*, not an EGV-success delta (`build217-impl-plan.md:222`). Finally, a soak can surface an **incident** that forces an unscheduled hotfix build outside the Ideas→Select path (build 218 S-0, a CRITICAL fork fix after a real CGM blackout, `build218-impl-plan.md:7`).

## 1. Fusion project settings (project-scoped for Trio-dev)

| Setting | Value | Why |
|---|---|---|
| `autoMerge` | **false** | Patches are stacked/regenerated by scripts and left uncommitted on `dev` until build+deploy+verify-live. Fusion must never push to `dev`. |
| `planApprovalMode` | **require-all** | Mirrors "user triggers each step and reviews between." Every plan parks for approval before execution. |
| `defaultWorkflowId` | **`builtin:coding-ideas`** (intake), promote into custom workflows below | Backlog-first intake; nothing auto-plans. |
| `ephemeralAgentsCanCreateTasks` | **false** | No runaway follow-up-task fan-out. |
| verification/test command | **`scripts/patch-test.sh` + static only** | AGENTS.md **rules 10 & 12**: never `xcodebuild`/`ci/local-build.sh` as routine verification. |
| commit attribution | **AI/`Co-Authored-By` trailers OFF**; keep only `Fusion-Task-Id` | AGENTS.md **rule 11**: no `Co-Authored-By: Claude` / `🤖 Generated with Claude Code`. |
| destructive MCP tools | **off** | Medical-device caution. |
| models | subscription OAuth + a review panel | No per-token cost; enables the review fan-out. |

## 2. Workflow A — "Trio Feature" (the 5-step pipeline)

Custom workflow whose nodes carry `docs/prompts/01–05` as node prompts, with **human gates between each**. **Each review node (Design Review, Pre-Impl, Red-Team) is an internal fix-and-update loop, not a single pass** — model it as a looping sub-node region that runs the prompt's mandated passes (01: ≥2, 3+ high-risk; 03: three non-collapsible phases to two-clean-consecutive; 05: ≥3) and self-terminates on the prompt's own verdict before parking for the human gate. **Reviewers edit the artifact by default (fix-and-update); report-only is opt-in and, for 03, is a distinct prompt (`03-pre-implementation-doc-review-report-only.md`), not a runtime flag.**

| Node | Trio step | Gate |
|---|---|---|
| Design Review | `01-design-doc-review` (≥2 adversarial passes, self-review, verdict clean/nits/needs-revision) | human approve |
| Create Plan | `02-create-implementation-plan` → writes the build/feature plan (`buildNNN-impl-plan.md` in the dominant per-build pattern, or `02-implementation-plan.md`) **with the Implementation-log as a section inside that plan doc** per `04:44-45` — there is **no** separate `03-implementation-log.md` node | parks for approval |
| Pre-Impl Doc Review | `03-pre-implementation-doc-review` (3-phase: finding→edit→regression; **design is source of truth**) | human PASS |
| Execute | `04-execute-implementation-plan` → code in `Trio` worktree, updates in-plan impl log; **verify = patch-test/static, no build, no commit-to-`dev`** | — |
| Red-Team Review | `05-implementation-changes-red-team` (≥3 passes, cross-patch type-resolution check) | human PASS → `in-review` |
| ~~Merge~~ | **disabled** — human runs patch scripts + build + verify-live, then moves docs to `completed/` | manual |

**Artifact caveat (grounded).** The real initiative uses per-**build** plan+log pairs keyed to the *predecessor build*, not a per-feature `00→04` chain; `00-feasibility.md`/`04-postmortem.md` are typically never created, and a single `01-design.md` is reused as an architecture touchstone across many builds. Do not gate the workflow on a fresh design doc per cycle. When wf-001 runs *inside* a build cycle (Workflow B), the **Design Review and Create-Plan nodes are optional/skippable** (`optional-group`); the usual entry point is Pre-Impl review of a plan drafted from the predecessor log + soak evidence.

Encode the **4-level severity** (blocker/major/minor/nit — uniform across `01/03/05`) and each prompt's **native verdict vocabulary** (`clean / clean with minor nits / needs revision|not clean`) as reviewer node config. Do **not** impose a literal `PASS` token or a `max 5 issues/pass` cap on the 01/03/05 nodes — those come from `doc-lifecycle.md`'s lightweight doc-review loop and a one-off feature prompt (`review-patch-protocol.md`) respectively, not from the deep-review prompts. If a lightweight doc-review lane is wanted, add it as a *separate* node type carrying the `doc-lifecycle.md` PASS/PATCH loop.

## 3. Workflow B — "Build Cadence" (soak review + ideation; research lane, not code)

| Node | Maps to | Fusion mechanics |
|---|---|---|
| **Soak Review** | Evidence base + a **per-task gate matrix** (the recurring soak-readout; labelled G1–Gn / A1–An / prose across builds — the count is **not** fixed, and it is authored in the prior build's **impl-log** then transcribed into the next **plan**) | research/analysis task (no worktree, no code) using **BetterStack MCP** that reads the prior build's readout and emits, **per candidate task**, a verdict in `{go, hold-sequence-later, low-priority, premise-confirmed, re-defer, killed}`; **human ratifies the matrix**. Not a single build-level GO/NO-GO |
| **Ideas Gathering** | `fable5-egv-ideation-prompt.md` | a governed **research run** with the ideation prompt; **checkpoint-first** (`fn_ask_question`/awaiting-input: restate constraints + top-3 signals, wait for go-ahead) *before* generating candidates |
| **Select** | rank survivors → candidates | human picks a **co-ship bundle** (often several arms + instrumentation) that becomes **one build's** plan feeding Workflow A. A selected item may be **instrumentation whose acceptance is "unblocks next-round ideas", not an EGV delta** — label it (`acceptanceType`) so its deferred review checks the right thing |
| **Soak Review (build N)** | deferred acceptance check | **this is the next cycle's Soak-Review node**, not a separate paired task: it **fans in** over *all* arms shipped in build N and emits both their acceptance and the next build's candidate-task gates. Acceptance may be **re-deferred** ("still can't tell — gate on the following soak"). One soak-review ≠ one ship-task |
| **Incident hotfix** (unscheduled) | a soak that surfaces a regression/incident | a build inserted **outside** Ideas→Select (e.g. build 218 S-0, a CRITICAL fork fix after a real CGM blackout, `build218-impl-plan.md:7`). Model as an edge Soak-Review → priority build-plan task, **bypassing** Ideas Gathering |

**Do-not-repeat memory:** store `egv-intervention-index.md` (everything tried/rejected/prohibited) and the per-build **graveyard** lists in Fusion **memory** (or keep on-disk and require the ideation prompt to read them). Enforces the "don't re-tread the graveyard" discipline mechanically — the main failure mode ("~8 of 10 fresh ideas die on contact").

## 4. Multi-model review fan-out (the biggest win)

Configure Fusion's reviewer lane as a **panel** (Opus for correctness/lifecycle, Sonnet for a second independent pass, a cheaper local/GLM model for breadth) on the Design/Pre-Impl/Red-Team nodes. This automates your manual "run it past 4 models," with the same evidence-required, no-padding discipline and the PASS/PATCH loop.

## 5. Verification config (rules 10 & 12)

Point Fusion's per-task verification at a thin wrapper (`scripts/fusion-verify.sh`) that runs **only** `scripts/patch-test.sh` (with its safety-path deletion audit) + static re-read checks, and **exits non-zero on any `xcodebuild` attempt**. Direct analog of Fusion's own `verify:fast` "test-free verification." Builds/TestFlight remain explicit human actions.

## 6. Worktree + patch-stack topology (the hard adaptation)

- Fusion project = **`Trio-dev`** (docs + patches + orchestration home, on `dev`).
- Code execution happens in the sibling **`Trio`** worktree (feature branches) + the **G7SensorKit fork**.
- Two options:
  - **(a) Review/orchestration-only (recommended to start):** Fusion drives the doc pipeline + review fan-out in `Trio-dev`; the actual code edit in `Trio` and patch integration stay human/Claude-via-MCP driven.
  - **(b) Workspace/multi-repo mode:** one Fusion task spans `Trio-dev` + `Trio` + G7SensorKit. More powerful; keep `autoMerge:false` and safety-path scope guards on.
- Either way: **"done" for Fusion = `in-review` with a PASS**; the human runs `mid-stack-update.sh --patch 09` / `repin-g7.sh` (patch 02) / `patch-test.sh` / build / verify-live. Fusion's file-scope enforcement (block mode) + a project rule "never edit `scripts/patch-audit.safety-paths` or `.waivers`" backstops the clobber guardrails.

## 7. Intake / backlog

`docs/backlog/<idea>/` ↔ Fusion **Ideas column** (Coding-Ideas workflow). Ideas land in Ideas → human review → promote into a "Trio Feature" or "Build Cadence" task, seeding `docs/in-progress/<feature>/`.

## 8. MCP, both directions

- **Inbound (linchpin):** register **BetterStack** as an MCP server *in Fusion* (token via a Fusion **secret reference** — never inlined) so soak-review and ideation agents run the telemetry queries (`source_id 1659391`, `t491594.trio`). Without this, neither cadence-loop stage works.
- **Outbound:** the Fusion operator MCP server (`fn mcp serve`) lets you drive all of this from Claude.

## 9. Safety rails (medical device)

- Destructive MCP tools off; `autoMerge` off; `planApprovalMode` require-all.
- Map the **patch-clobber safety-path audit** into the Fusion verify command; encode "agents may not edit the safety list/waivers" as a workflow rule + file-scope block.
- Carry the **Nightscout/diabetes safety guardrails**, the passive-observer contract, and "avoid confidently-wrong conclusions" discipline into executor/reviewer prompts.

## 10. What to explicitly disable (Fusion defaults that fight Trio)

- ❌ auto-merge (bypasses patch stack + clobber guards)
- ❌ hard-coding a `PASS` verdict or a 5-issue cap onto the 01/03/05 review nodes (verdict is `clean/nits/needs-revision`; passes are unbounded)
- ❌ modeling Soak-Review as a single build-level GO/NO-GO (it is a per-task, multi-valued gate matrix)
- ❌ any `xcodebuild`/full-build verification (rules 10, 12)
- ❌ AI-attribution commit trailers (rule 11)
- ❌ agent-created follow-up tasks
- ❌ destructive MCP tools
- ❌ Fusion scope-leak/merge touching patch/safety paths

## 11. Suggested rollout

1. **Phase 1 (near-zero risk):** BetterStack MCP inbound + use Fusion purely as the **multi-model review fan-out** over docs already in `docs/in-progress/`, `autoMerge:false`, no code execution. Directly replaces the manual "run it past 4 models" step.
2. **Phase 2:** the "Trio Feature" workflow with human gates; execution still human/Claude-driven.
3. **Phase 3:** the "Build Cadence" workflow (soak review + ideation research runs), intervention-index memory, deferred-soak acceptance pattern.
4. **Phase 4 (optional):** workspace-mode execution across `Trio-dev`/`Trio`/G7SensorKit.

## Open questions

- Whether to run Fusion execution in `Trio` worktree directly (workspace mode) or keep code edits human/Claude-driven (Phase-1/2 recommendation).
- How much of the intervention-index/graveyard to migrate into Fusion memory vs. keep on-disk with required-reading enforcement.
- Whether the deferred-soak acceptance check should be a scheduled task or a manually-opened follow-up.
