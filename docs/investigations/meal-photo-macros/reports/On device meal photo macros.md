# iOS 27 brings on-device meal-photo macros within reach

**Verdict: feasible with caveats.** As of iOS 27, which shipped 2026-09-14, an app can take a meal photo, pass it to Apple's on-device Foundation Models model, and get back a typed struct (description, carbs, protein, fat) on any Apple Intelligence iPhone. It needs no network, no API key, no model download inside Trio and no third-party LLM. The photo can stay in memory and be thrown away after analysis. Two documented iOS 27 APIs make this possible: image `Attachment`s in prompts and `@Generable` guided generation from an image. Nothing like it existed on iOS 26, where the developer API was text-only. The blocker is no longer plumbing. It is accuracy, safety and upstream acceptance. Nobody has published a food or macro benchmark for Apple's on-device model. Frontier cloud models, which are the accuracy ceiling, still miss the clinically relevant ±10 g carb window on 30–55% of mixed meals when given a photo alone. Fat is the hardest macro to estimate, and Trio turns fat and protein into delayed fat-protein units (FPUs), so those errors become extra insulin hours later. Third-party on-device VLMs (Gemma 4, Qwen3.5/Qwen3-VL) also work technically, but they load 3–4 GB into the same process as the insulin loop, under a per-process ceiling of about 6 GB, and crossing that ceiling kills the loop. Cloud models (bring-your-own-key Claude/GPT/Gemini) are the most accurate and cost fractions of a cent per photo, but they give up the privacy premise and fail when offline. For the personal fork, the Apple path is buildable now as a confirm-before-save pre-fill. For upstream, the Trio maintainers have said publicly that LLM-based carb entry will not land and that any meal AI would be "ML-based, not LLM-based" ([Trio#963](https://github.com/nightscout/Trio/issues/963)). An on-device model answers their privacy objection but not that one.

| Path | Technically feasible on latest iOS? | Main blocker |
|---|---|---|
| Apple Foundation Models, on-device (iOS 27) | **Yes**, through documented APIs | Accuracy unmeasured; guardrail false positives; availability states; upstream "no LLM" stance |
| Apple Private Cloud Compute model | Unclear | Image input undocumented; per-developer entitlement that each self-builder would presumably need |
| Siri / Apple Intelligence / Visual Intelligence | **No** programmatic path | No API to send an image and get values back |
| Third-party on-device VLM (MLX / llama.cpp) | Yes, with high engineering risk | Jetsam inside the loop process; 2.5–4 GB download; per-builder memory entitlement |
| Cloud BYO-key Claude/GPT/Gemini | Yes, and already shipped elsewhere | Privacy (about 30-day retention), offline failure, model churn, maintainer refusal |

## Apple's iOS 27 model can return typed macros straight from a photo

Image input to Apple's on-device model arrived at WWDC 2026. In WWDC26 session 241 Apple says the on-device model "gains vision". Images go into the existing prompt builder through `Attachment(...)` next to text. Accepted sources are `UIImage`, `CGImage`, Core Image types, CoreVideo pixel buffers and file URLs, at any size, with larger images costing more tokens and latency ([WWDC26 session 241](https://developer.apple.com/videos/play/wwdc2026/241/)). Session 237 shows `session.respond(generating: EventInfo.self)` driven directly by an image attachment, which is **guided generation from an image** ([WWDC26 session 237](https://developer.apple.com/videos/play/wwdc2026/237/)). A `@Generable struct MealEstimate { description; carbs; protein; fat }` is the same pattern. On-device requests have no request limits and run offline ([WWDC26 session 319](https://developer.apple.com/videos/play/wwdc2026/319/)). On iOS 27 the on-device context is **8,192 tokens**, though session 319 qualifies this as "for newer devices" and gives 4,096 on OS 26. That is enough for one photo, a short prompt and a small struct. Apple does not document how many tokens an image consumes or the maximum resolution, so the photo should be downscaled before it is attached.

Apple also ships building blocks that suit this feature. A `BarcodeReaderTool` and a 30+-language OCR tool plug into the model's tool calling. In Apple's demo the model could not read a QR code alone but could with the tool ([WWDC26 session 237](https://developer.apple.com/videos/play/wwdc2026/237/)). That opens a packaged-food or nutrition-label path inside the same flow. Vision itself has **no food, nutrition or captioning API**. Apple says open-ended description belongs to Foundation Models and fixed tasks belong to Vision. Its new tap-to-segment request could let a user isolate items on a plate ([WWDC26 session 237](https://developer.apple.com/videos/play/wwdc2026/237/)). No Apple API estimates portion size, volume or mass.

The routes that sound most "Apple AI" are closed. There is **no public API to send an image to Siri or Visual Intelligence and read back a result**. Visual Intelligence is user-initiated system UI. Third-party apps join it only as result providers, receiving a `SemanticContentDescriptor` with labels and a pixel buffer and returning their own entities ([Blake Crosley, third-party](https://blakecrosley.com/blog/app-intents-2-ios-26-additions)). Trio could register as such a provider so that a Visual Intelligence camera capture offers a "log in Trio" result. The analysis would still be Trio's own Foundation Models call. Apple's next-generation Foundation Models are based on Google's Gemini ([joint Google–Apple statement](https://blog.google/company-news/inside-google/company-announcements/joint-statement-google-apple/)), and "Siri AI" is listed as a beta server feature with daily limits ([Apple Support 121115](https://support.apple.com/en-us/121115)). Developers cannot reach either directly. Apple's own iOS 27 food feature, the Camera app's Siri mode, gives only a qualitative rating from very low to very high plus traits such as "high sugar". It shows **no calories or macros**, does not sync to Health, and has no developer API ([MacRumors iOS 27 Health guide](https://www.macrumors.com/guide/ios-27-health-app/)). Apple is cautious about gram estimates in its own product.

The new `PrivateCloudComputeLanguageModel` is the only first-party route to a bigger model. It has a 32K context and reasoning levels, uses the same `LanguageModelSession` API, and charges no per-token cost to apps under 2M downloads. It also needs internet, has a daily per-user quota, and requires an **entitlement applied for on the developer site**. Apple does not say whether it accepts images ([WWDC26 session 319](https://developer.apple.com/videos/play/wwdc2026/319/)). Every Trio user builds under their own team ID, so presumably every user would need their own entitlement. That is unconfirmed, and it makes PCC impractical for Trio until someone tests it.

Device and runtime limits set the edges of the feature. Apple Intelligence needs an iPhone 15 Pro/Pro Max, iPhone Air, or iPhone 16 or later. It also needs up to 8 GB of storage (14 GB on the 17 Pro/Air), matching device and Siri languages, and an account outside mainland China ([Apple Support 121115](https://support.apple.com/en-us/121115)). The model can be unavailable because the device is ineligible, Apple Intelligence is turned off, or the model assets are still downloading. Those reasons come from iOS 26 documentation and were not re-verified for iOS 27. The camera button has to handle each state by hiding itself or falling back to manual entry. Guardrails are a known problem. Developers report false positives on harmless content. One June 2026 report says `Generable` conversions began failing with guardrail violations around iOS 26.5, and that the permissive guardrail mode does not apply to `Generable` output ([Apple Developer Forums 835777](https://developer.apple.com/forums/thread/835777)). No report shows food or diabetes prompts being blocked. Still, the structured-output path cannot count on loosening guardrails, so it must handle a guardrail violation by falling back to manual entry. Apple's acceptable-use terms forbid inaccurate or dangerous outputs and unsupervised decisions with material impact in high-risk domains, medical included ([Apple AUP](https://developer.apple.com/apple-intelligence/acceptable-use-requirements-for-the-foundation-models-framework/)). A pre-fill that the user always reviews fits that rule. Dosing automatically from a photo arguably does not.

## Accuracy, not plumbing, is the binding constraint

The best evidence on photo carb estimation comes from frontier cloud models. On composite meals they reach roughly **9–18 g mean absolute error, with only 45–70% of estimates within ±10 g**. On simple single foods they do far better. GPT-4o got 93% of fruit and vegetable items within ±10 g but only 47% of composite meals, and adding a size-reference object did not help the composite meals ([Johansen et al., JDST 2026](https://doi.org/10.1177/19322968261424270)). ChatGPT-5 on 150 dietitian-weighed Singaporean meals had an **8.7 g MAE, 69% within ±10 g, and a significant +2.8 g overestimation bias** ([Lian et al., Front Nutr 2026](https://www.frontiersin.org/journals/nutrition/articles/10.3389/fnut.2026.1927840/full)). On 246 hospital meals, ChatGPT-5 had an 18.0 g MAE, against 13–14 g for dedicated diabetes apps ([Joubert et al., DOM 2026](https://doi.org/10.1111/dom.70396)). In a controlled-feeding set of 806 meals, Claude 3.7 Sonnet, GPT-4o and GPT-4.1 all landed at **23–25 g carb MAE** ([ACETADA, arXiv 2507.07048](https://arxiv.org/html/2507.07048v1)). At a 1:10 carb ratio, that is 2–2.5 U of potential bolus error.

Those numbers matter against the clinical thresholds. A 10 g swing around a 60 g meal made no measurable glucose difference. Dosing for 60 g when the meal was 40 g or 80 g produced significantly more hypoglycaemia or hyperglycaemia, which led the authors to recommend staying within 10 g ([Smart et al., Diabet Med 2012](https://onlinelibrary.wiley.com/doi/10.1111/j.1464-5491.2012.03595.x)). People with T1D counting by eye err by about 15 g per meal ([Brazeau et al. 2013](https://www.researchgate.net/publication/233403794_Carbohydrate_couting_accuracy_and_blood_glucose_variability_in_adults_with_type_1_diabetes)), ranging from 8.3 g in a skilled Turkish cohort ([Soyer et al., DRCP 2026](https://www.sciencedirect.com/science/article/abs/pii/S0168822726001993)) to 27.9 g on restaurant-style meals ([Rhyner et al., JMIR 2016](https://jmir.org/2016/5/e101)). An AI pre-fill from a photo alone is therefore **about as good as an average unaided guess**. It helps poor estimators and does little for good ones. Automated insulin delivery absorbs part of moderate errors: a 12-person pilot found no significant time-in-range difference between carb counting and qualitative meal-size estimates ([Schumacher et al., DT&T 2026](https://doi.org/10.1177/15209156261456440)). It does not protect against a large overestimate that front-loads a bolus.

The biggest single lever is a short text hint from the user. Gemini's MAE fell from **6.55 g on the photo alone to 2.14 g with a meal description**, beating patients ([Soyer et al. 2026](https://www.sciencedirect.com/science/article/abs/pii/S0168822726001993)). GPT-4o's MAPE fell from 34.8% to 13.7% as ingredient detail was added ([Tecce et al., Diabetes Care 2025](https://diabetesjournals.org/care/article/48/8/e97/160531/AI-Powered-Carbohydrate-Counting-for-Type-1)). Giving the model the true weight cut carb MAPE from 56.6% to 20.2% ([Mu et al., ACM BCB 2025](https://pubmed.ncbi.nlm.nih.gov/42502812/)). The dominant error is portion size, and a better model does not fix it. The same photo also does not give the same answer twice. Run-to-run and viewpoint variance stayed "nonnegligible" for GPT-4o and GPT-5.1 even with deterministic settings ([Wang, Lane, Waki, JMIR Diabetes 2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC13544413/)). One DIY developer reported a 40 g spread across 12 submissions of the same photo, in unpublished work ([iAPS#1742](https://github.com/Artificial-Pancreas/iAPS/pull/1742)).

Fat and protein are worse, and that matters in Trio because of FPUs. In relative terms, fat is consistently the hardest macro: its coefficient of variation was 24%, against 18% for protein and 15% for carbs ([Chen et al., AJCN 2025](https://doi.org/10.1016/j.ajcnut.2025.10.013)). Oil, dressing and absorbed cooking fat are invisible in a photo ([Nakagawa & Yamamoto, Nutrients 2026](https://www.mdpi.com/2072-6643/18/17/2892)). Direct-prompting baselines on Nutrition5k show about 66% fat error ([Open-KNEAD preprint](https://arxiv.org/pdf/2607.12911)). Under a common convention of 100 kcal of fat and protein to about 10 g of carb equivalents, overestimating fat by 15 g adds roughly 13.5 g of extended carb equivalents. That becomes delayed insulin, the kind of overbolus a user is least likely to notice. Trio's actual FPU factor and delay settings were not checked in this pass. No study has validated photo-derived fat or protein in a diabetes population or measured the dosing effect of FPU errors.

The most important gap is **Apple's own model**. No published benchmark covers food recognition or macro estimation by the iOS 27 on-device model, and Apple gives no parameter count. The 2025 on-device model was about 3B parameters ([Apple tech report 2025](https://arxiv.org/pdf/2507.13575)). Untuned small open VLMs score well below frontier models on food. Qwen3-VL-8B's calorie error on CalorieBench was more than double GPT-4o-mini's ([Food-R1, arXiv 2606.04986](https://arxiv.org/html/2606.04986v1)). Its macro-gram MAPE on homemade food was about double GPT-5.1's ([OmniFood-Bench, arXiv 2607.08423](https://arxiv.org/html/2607.08423v2)). If a 3B-class Apple model follows that pattern, its descriptions may be usable for common dishes while its gram estimates are materially worse than cloud. That is an extrapolation, and only a test against weighed meals can settle it. Domain fine-tuning closes much of the gap: Food-R1 halved GPT-4o-mini's calorie error from an 8B base. So does grounding numbers in a nutrition database: NutriDish reached a 5.9 g MAE ([Lian et al. 2026](https://www.frontiersin.org/journals/nutrition/articles/10.3389/fnut.2026.1927840/full)). Apple's model can be steered with prompts and tools but cannot be fine-tuned through this API.

## Third-party on-device VLMs work but endanger the insulin loop

Open VLMs now run on iPhones. MLX Swift (`mlx-swift-lm`, MIT) registers 22 VLM architectures, including Gemma 4, Qwen3-VL and Qwen3.5 ([VLMModelFactory.swift](https://raw.githubusercontent.com/ml-explore/mlx-swift-lm/main/Libraries/MLXVLM/VLMModelFactory.swift)). llama.cpp's prebuilt XCFramework can include its multimodal library ([Liquid AI docs](https://docs.liquid.ai/deployment/on-device/llama-cpp/mobile)). A September 2026 developer test ran **Gemma 4 E2B 4-bit on an iPhone 16 Pro at about 5.5 s per photo with 3.5 GiB peak memory**, slowing to 5.8 s as the phone heated ([hermit issue #2](https://github.com/JaviChulvi/hermit/issues/2)). The realistic shortlist is Gemma 4 E2B and the 2B variants of Qwen3.5 and Qwen3-VL, all Apache 2.0. Apple's FastVLM weights are licensed for research only and should be excluded ([LICENSE_MODEL](https://raw.githubusercontent.com/apple/ml-fastvlm/main/LICENSE_MODEL)). None of these small models has been benchmarked on carbs, protein or fat. No VLM measurement exists for the 8 GB iPhone 15 Pro.

The deciding problem is memory. Developers measured a **per-process ceiling of about 6,144 MB on 8 GB and 12 GB iPhones even with the increased-memory-limit entitlement** ([Apple Developer Forums 834805](https://developer.apple.com/forums/thread/834805)). One Gemma 4 build avoided jetsam only after its GPU buffer cache was cut from 512 MB to 64 MB. When a process crosses the limit, iOS kills the whole process, and app extensions have much lower limits ([Apple jetsam docs](https://developer.apple.com/tutorials/data/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports.md)). Trio's loop, pump and CGM drivers and BLE sessions share the app process. An out-of-memory kill during inference stops the loop until iOS relaunches the app. A model left loaded in the background also makes Trio the obvious target when the system reclaims memory. Running the model safely would mean loading it only on demand and checking free memory with `os_proc_available_memory()` first. It would also mean unloading it on backgrounding and on memory warnings. Each self-builder would need to add the memory entitlement to their own App ID ([Apple entitlement docs](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit.md)). On top of that, each user downloads a 2.5–4 GB model with a pinned revision. Apple-hosted Background Assets are tied to an App Store Connect record, and one developer reported a 68% completion rate with them ([Forums 845723](https://developer.apple.com/forums/thread/845723)).

Apple's Foundation Models avoids all of this. The model is a system asset that Apple downloads and updates, so Trio never bundles or loads the weights. Whether its inference memory counts against Trio's process budget is not documented, so it should be measured, not assumed. One hybrid stays attractive for later: Apple's model or a small VLM names the foods, and a tiny regressor or a database lookup supplies the numbers. CalorieK, for example, is a 94M-parameter MIT regressor reporting a 6.3 g carb MAE on Nutrition5k, though that figure is self-reported and in-distribution ([Dralkh/CalorieK](https://huggingface.co/Dralkh/CalorieK)). That design also fits what maintainers mean by "ML-based".

## Cloud models are the accuracy ceiling but break the privacy premise

The cloud baseline is cheap and the most accurate option available. A 1,000×1,000 image is about 1,300 tokens on Claude, which works out to **about $1.30 per 1,000 images on Haiku 4.5** ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). Gemini Flash-class models cost $0.10–0.59 per 1,000 images ([bioRxiv 2026](https://www.biorxiv.org/content/10.64898/2026.07.26.740845v1)). Cost does not matter for one user. Frontier cloud models lead every food benchmark found, but their best realistic performance is still the ~9–25 g carb error described above.

The costs are elsewhere. By default, Anthropic and OpenAI keep API inputs for up to about 30 days ([Anthropic retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data); [OpenAI: Your data](https://developers.openai.com/api/docs/guides/your-data)). Gemini's free tier allows content to be used to improve products ([Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)). "Photo discarded after analysis" is therefore true only on the phone. The feature fails completely offline, which is exactly when a fast estimate is wanted at a restaurant with poor signal. Model churn is a real maintenance cost: Loop users lost Gemini when a hard-coded Gemini 1.5 model was deprecated ([Loop#2329](https://github.com/LoopKit/Loop/pull/2329)). In iOS 27, Anthropic and Google publish Swift packages that plug into the same `LanguageModelSession` API ([WWDC26 session 241](https://developer.apple.com/videos/play/wwdc2026/241/)). One code path could therefore run on-device by default and offer cloud as an opt-in. That is the cleanest way to keep the comparison baseline without building a second integration.

## Upstream Trio has drawn a line at LLM carb entry

For the personal fork, nothing blocks a build except doing the work. For upstream, the record is unusually explicit. In December 2025 the maintainers closed Claude-based PRs, including photo carb estimation. They said they would not accept anything that requires users to add an LLM, and that features which influence insulin dosing are a line a generic LLM integration cannot cross ([Trio#888](https://github.com/nightscout/Trio/pull/888#issuecomment-3651397154)). In February 2026 dnzxy added that LLM-based carb recording or dosing prompts won't land, that future meal features would be "ML-based, not LLM-based", and that oref is built to work with estimates ([Trio#963](https://github.com/nightscout/Trio/issues/963)). An OpenFoodFacts barcode PR was told to remove its ML parts and was later closed as too large and vibe-coded ([Trio#874](https://github.com/nightscout/Trio/pull/874)). Trio's CONTRIBUTING.md rejects PRs that are largely AI-generated ([Trio CONTRIBUTING](https://github.com/nightscout/Trio/blob/dev/CONTRIBUTING.md)). Sam King has said he would rather move toward no meal announcements at all, and suggested a separate app talking to Trio over IPC ([Trio#874](https://github.com/nightscout/Trio/pull/874)). An on-device, photo-discarding design answers the privacy and bring-your-own-key objections. It does not answer the "no LLM" objection, because Apple's model is an LLM. The maintainers have made no public statement about Apple's on-device model specifically, and their Discord is not public.

Prior art shows both how to build this and where it stalls. Loop's FoodFinder was cloud BYO-key and had a clear safety model. It never bolused, only pre-filled, showed a confidence score, left every value editable, and was off by default. It was never merged and now lives in the LoopPowerPack fork ([Loop#2404](https://github.com/LoopKit/Loop/pull/2404)). Its most reusable idea is logging the AI's original carb value next to the confirmed value. That lets a builder measure AI-versus-user error without keeping any photo ([FoodFinder_DEVELOPER.md](https://github.com/LoopPowerPack/Loop/blob/main/Documentation/FoodFinder/FoodFinder_DEVELOPER.md)). iAPS shipped cloud photo analysis in v8.2.0. It uses an itemized schema with per-item confidence, per-100 g macros, editable portions and optional text hints, and it shipped over a public safety objection ([iAPS#1742](https://github.com/Artificial-Pancreas/iAPS/pull/1742)). No diabetes app was found using Apple's on-device model or any on-device VLM for meals, so a Trio implementation would be the first and would have no field data. Regulated vendors stay well short of a gram number feeding a dose. Dexcom's feature only describes ingredients ([Dexcom](https://investors.dexcom.com/news/news-details/2025/Dexcom-Launches-Revolutionary-AI-Powered-Meal-Logging-Feature-Across-Glucose-Biosensing-Portfolio/default.aspx)), Abbott's gives a three-colour impact rating ([Abbott](https://abbott.mediaroom.com/2026-01-05-Abbotts-new-Libre-Assist-app-feature-tackles-a-top-need-for-people-living-with-diabetes-in-the-moment-food-decisions?asPDF=1)), and SNAQ disclaims insulin-dosing use ([SNAQ App Store](https://apps.apple.com/us/app/snaq-diabetes-food-tracker/id1465916014)). FDA-cleared bolus calculators show that dose calculation from carbs is a device function ([FDA K222888](https://www.accessdata.fda.gov/cdrh_docs/pdf22/K222888.pdf)). A DIY build differs, but the confirm-before-save norm still applies.

An upstream contribution would therefore need a short design document before any code: a problem statement, a safety model, a user flow and an integration strategy, which is what dnzxy and kingst asked for. It would need a small, hand-reviewable PR, and data from the personal fork showing AI-versus-confirmed deltas. Framing it as an optional, off-by-default suggestion would help. Another route is a separate companion app that hands confirmed values to Trio, which avoids the "LLM inside the AID" objection altogether.

## Next steps / not yet done

This pass researched capability only. Two pieces of planned follow-up work were **deliberately not done**. The first is mapping Trio's code hook points: the add-treatments screen, the quick-pick treatments modal opened by long-pressing the main-screen plus button, and how pre-filled carbs, fat and protein flow into the bolus calculator and FPU conversion, including whether a written meal description has anywhere to go. The second is a rough UX and design sketch of the capture, review and confirm flow. Nothing in this report describes Trio's code, and those details should come from reading the Trio source, not from this document. Beyond those two items, the next highest-value step is an empirical one. Run the iOS 27 on-device model against a small set of weighed home meals, photo only and photo plus a one-line description, five or more runs each. Record carb, protein and fat error and the spread between runs, and compare against one cloud model. Do this before committing to any UI. Measure latency and the memory footprint of Trio's process during inference on the oldest supported phone in the same test.

## Conclusion

The question has moved. Before WWDC 2026, on-device meal-photo macros on an iPhone meant shipping a multi-gigabyte VLM inside an insulin-dosing process, a risk that is hard to justify. iOS 27 removes that risk by giving every Apple Intelligence iPhone a system-managed vision model with typed output. What is left is an evidence problem, not an engineering one. No one knows how good Apple's model is at food, and the best models anywhere are only about as good as an average person's guess unless the user adds a description. So the photo is best treated as a way to get a description and a first draft, with the user's own one-line hint doing most of the accuracy work. Fat and protein should be shown as lower-confidence than carbs, because FPU errors become insulin delivered hours later. Logging AI-versus-confirmed values from the personal fork is also the only realistic way to produce evidence the upstream maintainers might accept. That evidence will matter more to them than the privacy benefit of running on-device.
